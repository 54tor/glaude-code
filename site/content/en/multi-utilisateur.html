Accounts and multi-user

By default, a single token gives access to everything. The optional multi-user mode lets several people sign in, each with their own account, a mandatory second factor and independent rights per Claude configuration folder.

Read what the rights protect, and what they do not first: exec and config_write are equivalent to the system account that runs gld.

Enable

Nothing changes as long as no account exists. The mode is enabled by creating the first account, on the command line, never from the web interface:

gld user add --admin alice

The password is requested twice, without echo: 12 characters minimum, and passwords from the embedded list of the most common ones are refused. The running server notices within 2 seconds at most; the sign-in form then replaces the token for the browser.

An administrator has no access to a configuration folder by default: grant yourself rights.

gld user grant alice main mem_read mem_write usage_read sessions_read

main designates the main folder; for another one, give its name. The Accounts screen of the interface (administrators) does the same afterwards.

CommandEffect
gld user add [--admin] <name>creates an account
gld user listlists accounts
gld user disable|enable <name>disables or re-enables
gld user passwd <name>changes the password
gld user reset-mfa <name>erases TOTP, security keys and backup codes, closes sessions
gld user grant [--yes] <name> <home> <rights…>grants rights
gld user revoke <name> <home> <rights…>removes rights

Sign in

  1. Name and password.
  2. Second factor, mandatory: a TOTP code, a WebAuthn security key (hardware key, passkey) or one of the 10 backup codes (single-use, shown once).
  3. An account with no factor enrolls one at first sign-in and receives its backup codes.

Enrolling the first factor only requires the password: create the account right before the person's first sign-in (or enroll them yourself), and do not leave an account with no factor lying around.

  • Adding or removing a factor, changing one's password or regenerating one's codes requires reauthentication: password and code.
  • Sessions expire after 12 h of inactivity, and after 30 days at the latest. Disabling an account, resetting its factors or changing its password closes its sessions.
  • Brute-force protection: after repeated failures, sign-in is temporarily blocked, with an identical message whatever the cause.

The nine rights

Nine independent rights, per (account, configuration folder) pair. A missing right means denied.

RightOpens
mem_readMemory, rules, snippets (read), notes, trash (read), health, reading the folder's configuration
mem_writeWrite, move, merge, delete CLAUDE.md, rules, memory, notes; empty the trash
mem_syncSync between configuration folders (requires mem_read on the source, mem_write on the destination)
usage_readAccount and consumption, never the content of conversations
sessions_readTranscripts, session state, search
config_writeSettings and skills (hooks, MCP servers, permissions), snippets, raw editing, restoring a backup
execChat, new session, web terminal, sending keys, git push, renaming and deleting sessions, browsing the disk
fs_readRead a project's tree and files, .env and keys included
fs_writeWrite, create, rename and delete a project's files. Does not imply fs_read
  • An administrator manages accounts and rights but has no implicit access to folders.
  • The server refuses to grant mem_write or config_write to an account without mem_read on the same folder.
  • Rights are attached to a configuration folder's identifier, not to its name.

What the rights protect, and what they do not

exec and config_write are equivalent to the system account that runs gld. Writing a hook, an MCP server or a skill, or opening the chat or the web terminal, runs code under that user: the person can read and write the authentication database and the key. Only grant these two rights to people you trust.

mem_write executes nothing, but memory and rules files are instructions that every Claude session in the folder loads. Granting it amounts to being able to steer what other people's sessions do.

A co-user limited to memory, usage and reading sessions has no path to the accounts database.

Administration and log

Where the data lives

  • The authentication folder is GLD_AUTH_DIR if set, otherwise the OS configuration folder followed by gld (Linux ~/.config/gld). It contains the auth.db database (SQLite). It is distinct from CLAUDE_CONFIG_DIR: backing up or syncing a configuration folder does not carry the accounts.
  • TOTP secrets are encrypted and sensitive rows are signed with a master key (the GLD_AUTH_KEY variable, the OS keyring, or the auth.key file by default).
  • gld never silently falls back to open mode: if the database is deleted or tampered with while gld is running, the service is refused (503) until restart.
  • Lost key: gld user reset-mfa cannot help. Recover the key (backup, original value of GLD_AUTH_KEY); otherwise, move the database out of the folder and recreate the first account: accounts, factors and rights have to be redone.

What about the token?

With accounts, the token is no longer used by the browser: it only counts as an Authorization: Bearer header (automation), and only if it is set through GLD_WEB_TOKEN. It grants all rights on every folder, never administration.

Several configuration folders

Each configuration folder ("home") has its own sessions, memory and rights. Creating or removing a folder is reserved to administrators; other users only see the ones where they have at least one right.
